# 足迹拼图（省 / 地级市 / 区县三级）

选一批旅行照片，按照片里的 GPS 位置自动定位到区县，并把照片拼进行政区轮廓里。可以在“省（34）/ 地级市（395）/ 区县（3235）”三个层级之间切换，照片只需导入一次。纯前端，照片不上传，只存在浏览器的 IndexedDB 中。

## 用法

用浏览器打开 `index.html`（同目录需要 `china-admin.js` 和 `vendor/topojson-client.min.js`），或放到任何静态托管。

- **添加照片（按位置自动归属）**：读取 JPEG 的 EXIF GPS，定位到区县，地级市和省随之确定。没有定位的照片进入“待分配”，可以手动选到省 / 市 / 区县。
- **切换层级**：省 / 地级市 / 区县，计数和拼图随之变化，每张地图记住自己的层级。
- **点省份**：进入省内视图，看该省各市/区县的点亮情况；选中一个单元可以单独添加照片、重排、清空。
- **多张地图**、**生成分享图**（1500×1500 PNG）。

## 地图数据

`china-admin.js` 由 `tools/build_admin.js` 生成，对账报告在 `tools/admin-report.txt`。

- **几何**：`echarts-china-counties-js@1.0.2`（npm，MIT 声明），约 3250 个县级多边形。从内容判断是 **2017–2018 年前后** 的区划（例如还有莱芜市、济阳县、会理县）。原始数据的最终来源未注明，MIT 声明不一定能覆盖底层测绘数据。
- **名称与归属**：`zoningjs@3.2025.0`（民政部 2025 年县以上行政区划代码，MIT）。对账规则：
  1. 代码一致 → 直接采用新名称；
  2. 同一地级（或其改名后的继任者）内按地名主干匹配，例如济阳县→济阳区、会理县→会理市；
  3. 人工白名单：确定的一对一改名（如宜宾县→叙州区）、整体并入（如港闸区→崇川区）、跨地级划转（公主岭→长春、莱芜→济南）；
  4. 仍对不上的（2017 年后被**拆分重划**：大同城区/矿区/南郊区、长治城区/郊区、伊春 2019 年调整、杭州江干区、邢台县等共 23 个）保留旧名和旧边界，界面上标“旧”。
- **几何缺失**：2025 年新设的单元中，凡是由拆分产生的（如大同平城区/云冈区、长治潞州区），没有对应几何。
- **处理**：TopoJSON 简化（保留约 2% 的点），三层共用同一套弧线。地级和省的形状在浏览器里由县级多边形组合，边界线用 `topojson.mesh` 取。
- **特殊处理**：金门在源数据里重复出现（福建泉州 + 台湾乡镇），保留前者；马祖归福州市连江县。直辖市和港澳的“地级单元”就是它们自己。
- **台湾**的县级单元按区划代码是乡镇市区（358 个），所以区县总数 3235 比大陆县级单元数（约 2840）多。

## 已知限制

- 只解析 JPEG 的 GPS。HEIC 原图在 Chrome 里无法解码；iOS 选图时是否保留位置取决于系统和选项。微信传过的图、截图一般没有 GPS。
- 边界是简化后的低精度数据，区县交界附近（几百米内）的照片可能被分到隔壁。海岸附近用“0.5° 内最近的区县”兜底。
- 照片压缩到长边 640px 存储；数据只在当前浏览器里。

## 地图合规（公开发布前必读）

这些边界数据**没有审图号**，而且不是最新区划。按《地图管理条例》，在中国境内公开展示/发布地图一般需要送审，或者使用自然资源部“标准地图服务”的底图。自己用没问题；公开上线前请替换为合规底图。

## 重新生成

```bash
npm i topojson-server@3.0.1 topojson-simplify@3.0.3 topojson-client@3.1.0 opencc-js@1.0.5
npm pack echarts-china-counties-js@1.0.2 zoningjs@3.2025.0   # 解包得到 src/ 与 0.json
node tools/build_admin.js <counties>/package/src <zoning>/package/0.json china-admin.js tools/admin-report.txt
# KEEP=0.04 可以保留更多细节（文件更大）
```
